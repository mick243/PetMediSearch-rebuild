# 백엔드 재설계 계획 (2026-09-28)

받은 피드백 세 가지를 이 순서로 적용합니다.

1. **Prisma 도입** — DB 관리와 CRUD 레이어를 세우고, 날것의 SQL 이 흩어진 백엔드를 다시 짭니다.
2. **데이터 마이그레이션** — 스키마 변경과 데이터 원천(시드·적재)을 파일로 관리하고, 둘의 관계를 정합니다.
3. **토큰 최적화** — 데이터를 쪽 단위로 나눠 보냅니다. API 응답과 AI 요약 입력 둘 다입니다.

정한 것: **Prisma 7 + 서버를 TypeScript(ESM)로**, **단계마다 PR**. 단계는 아래 표 순서로 갑니다.

## 미리 정해 둔 것

**날짜.** Prisma 는 `DATETIME`·`TIMESTAMP` 를 UTC 로 읽어 Date 로 돌려줍니다. DB 에는 한국 벽시계가 들어 있습니다.
- 읽을 때: UTC 필드로 다시 문자열을 만들어 지금과 같은 모양을 냅니다.
- 쓸 때: `@default(now())` 는 Prisma 가 UTC 로 값을 채웁니다. 그래서 DB 기본값(`CURRENT_TIMESTAMP`)에 맡깁니다.
- 기준선의 `<방금>` 은 방금 쓴 행이 지금 한국 시각과 10분 안일 때만 붙어서, 9시간 어긋나면 잡힙니다.

**숫자와 참거짓.** Prisma 의 Decimal 은 `3.2` 처럼 뒷자리 0 을 버리고, `tinyint(1)` 은 `true`/`false` 로 끌어옵니다. 둘 다 지금 모양(`'3.20'`, `0`/`1`)으로 맞춥니다.

**큰 컬럼.** 반려동물 사진, 후기 사진, 이모티콘 그림은 목록에 딸려 오지 않게 합니다. 방법은 두 가지를 같이 씁니다.
- 클라이언트 전체에 `omit` 을 겁니다.
- 목록 쿼리는 필요한 컬럼만 `select` 합니다.
- 까닭: 한 번 새면 후기 목록이 14.4MB 가 됐던 자리입니다(CLAUDE.md §1.1).

**SQL 로 남길 곳.** 아래는 ORM 으로 옮기지 않습니다. TypedSQL(`prisma/sql`)로 타입만 붙여 둡니다.
- 재귀 CTE(댓글 스레드)
- 지도 검색·격자
- `JSON_LENGTH`
- `INSERT … SELECT`(탈퇴 계정 거르기)
- 이모티콘 번호 당기기

모두 이미 재고 다듬은 쿼리입니다.

**권한.** 앱 계정은 행 읽기·쓰기만 있습니다(`scripts/createDbUser.js`).
- `prisma migrate` 는 root 로 돌립니다(`prisma.config.ts` 의 접속 정보).
- 앱이 실행 중에 쓰는 접속은 앱 계정입니다.

**마이그레이션 기준선.**
- 신규 설치 스키마(`createTables.sql`)를 `0_init` 으로 둡니다.
- 이미 돌고 있는 DB 에는 `migrate resolve --applied 0_init` 로 적용된 것으로 표시합니다.
- `alter*.sql` 은 이력으로 남깁니다.
- 이름순으로 돌리면 순서가 깨지는 문제(예: `alterEmoticonHash` 가 `alterEmoticons` 보다 먼저 돎)는 적용 기록 표가 생기면서 없어집니다.

**MySQL 판.** compose 의 `mysql:8` 은 이제 8.4.11 을 받습니다. 기준선도 8.4.11 로 돕니다. 개발 DB(8.0.46)는 따로 올려야 합니다.

## 하지 않는 것

- 응답의 키 이름이나 타입을 바꾸지 않습니다. 화면이 그대로 받아야 합니다. 바꿀 것이 보이면 따로 묻고 합니다.
- 운영 DB 에 마이그레이션을 걸지 않습니다. 기준선 표시(`resolve`)는 사람이 확인하고 돌립니다.
- 공유 개발 DB 에 시험 데이터를 넣지 않습니다. 기준선은 전용 컨테이너(`petmedisearch_contract`)에서만 돕니다.
