# 부하 시험 (2026-09-15)

동시 사용자 200명까지 걸어 본 기록입니다. **서버는 버팁니다** — 200 VU 에서
실패 0건, 전체 p95 42ms, 예산을 넘긴 화면 없음.

다만 버틴다는 것과 여유가 있다는 것은 다릅니다. CPU 와 전송량이 어디로 가는지
갈라 보니 둘 다 한두 곳에 몰려 있었고, 그게 이 문서의 나머지입니다.

도구와 스크립트는 `loadtest/` 에 있습니다 (쓰는 법은 `loadtest/README.md`).

---

## 어떻게 쟀나

| 항목 | 값 |
|---|---|
| 대상 | `server/` API. 화면은 Vercel 정적 호스팅이라 여기서 잴 것이 없습니다 |
| DB | 사본 `petmedisearch_scale` — 사용자 10,007 · 글 20,000 · 댓글 60,000 · 후기 15,000 · 아이 6,000 · 접종 일정 30,000 · 시설 31,493 |
| 서버 | Node 24.18 · `NODE_ENV=production` · `DB_POOL_SIZE` 기본값 10 · `UV_THREADPOOL_SIZE` 기본값 4 · `TRUST_PROXY=1` |
| 부하 도구 | k6 v2.2.0 |
| 기계 | Core Ultra 9 185H (논리 22코어) · 31.5GB · k6·API·MySQL 이 모두 한 대 |

여정 비율은 지도 45% · 커뮤니티 30% · 마이페이지 15% · 로그인 6% · 쓰기 4% 입니다.
열 번에 두 번은 제일 무거운 쪽(후기 200건이 몰린 시설, 댓글 300건이 달린 글)을
고르게 했습니다.

### 이 숫자를 곧이곧대로 믿으면 안 되는 부분

- **네트워크가 없습니다.** 전부 localhost 이고 TLS 도 없습니다. 실제 배포에서는
  여기에 왕복 지연과 TLS 악수가 더해집니다. 아래 지연 값은 **서버가 쓴 시간**이지
  사용자가 기다리는 시간이 아닙니다.
- **화면은 재지 않았습니다.** React 가 마커 300개를 그리는 비용은 여기 없습니다.
- **한 대에서 다 돌았습니다.** k6 가 CPU 를 나눠 쓰므로, 여유가 실제보다 적게
  보일 수는 있어도 많게 보이지는 않습니다.
- 브라우저로 눈으로 확인한 것은 없습니다. API 응답만 봤습니다.

### 요청 제한을 어떻게 피했나

`generalLimiter` 는 한 주소에서 1분에 300번입니다. 한 대에서 200 VU 를 돌리면
전부 `::1` 한 사람으로 묶여 30초 만에 429 만 돌아옵니다 — 그러면 재는 것이 서버
성능이 아니라 `express-rate-limit` 의 처리 속도가 됩니다.

서버를 `TRUST_PROXY=1` 로 띄우고 k6 가 VU 마다 다른 `X-Forwarded-For` 를 붙여,
VU 하나가 사용자 한 명으로 세게 했습니다. 운영도 프록시 뒤에 있어 같은 경로입니다.
**모든 시험에서 429 는 0건이었습니다** — 요청 제한이 결과를 오염시키지 않았습니다.

## 찾은 것

### 1. CPU 의 74%를 로그인이 씁니다

램프 시험 동안 서버가 쓴 CPU 는 318.5초였습니다. 그중

| | 요청 수 | CPU |
|---|---|---|
| 로그인 | 834건 (전체의 **1.7%**) | 236초 (**74%**) |
| 나머지 전부 | 48,267건 | 82초 (요청당 1.71ms) |

이 기계에서 `bcrypt.compare` cost 12 는 **283ms** 입니다 (10회 평균). 로그인
응답시간 p50 298ms 가 거의 그대로 bcrypt 시간입니다 — 쿼리도 직렬화도 아닙니다.

**고칠 것은 아닙니다.** cost 12 는 일부러 고른 값이고, 낮추면 그만큼 무차별
대입이 쉬워집니다. 다만 용량을 늘릴 때 무엇을 봐야 하는지가 여기서 갈립니다.

- 읽기가 늘어나는 것은 거의 공짜입니다 (요청당 1.71ms).
- **로그인이 늘어나는 것이 비쌉니다.** 동시 접속이 아니라 *로그인 빈도*가
  이 서버의 CPU 를 정합니다.
- `bcrypt` 는 libuv 스레드풀에서 돌아 이벤트 루프를 막지는 않습니다. 대신
  `UV_THREADPOOL_SIZE` (기본 4)가 동시 로그인 수의 상한입니다. 초당 14건을
  넘기면 (4 ÷ 0.283초) 로그인이 줄을 서기 시작합니다.
- 이번 시험의 로그인은 초당 1.3건이었습니다. 상한의 10분의 1입니다.

토큰 유효기간이 1일이라 사람마다 하루 한 번 로그인한다고 보면, DAU 2000 은
하루 2000번입니다. 저녁 두 시간에 절반이 몰려도 초당 0.14건 — 여유가 큽니다.

### 2. 전송량의 90%가 지도 요청 둘에서 나옵니다

200 VU 2분 동안 428MB 가 흘렀습니다. 화면별 실측 크기로 갈라 보면

| 화면 | 한 번 | 2분 동안 | 몫 |
|---|---|---|---|
| `GET /facilities` (화면 범위, limit 300) | **139,598 B** | 1,987건 → 277MB | **65%** |
| `GET /reviews/:id/images` | 214,064 B | 498건 → 107MB | **25%** |
| `GET /category?category=` | 15,320 B | 1,358건 → 21MB | 5% |
| `GET /pets` | 27,774 B | 655건 → 18MB | 4% |
| `GET /facilities/clusters` | 5,180 B | 1,987건 → 10MB | 2% |

지연은 문제가 없습니다(p95 15ms). localhost 라 전송이 공짜였기 때문입니다.
**실제 망에서는 이 두 줄이 그대로 사용자의 대기 시간이 됩니다** — 140KB 는
LTE 에서 1초가 넘습니다.

`review-images` 는 설계대로입니다. 목록에는 장수만 싣고 펼칠 때만 받아가므로
(`server/controller/review.js:76`), 받는 사람은 실제로 펼친 사람뿐입니다.

### 3. `/facilities` 응답의 31%는 화면이 쓰지 않습니다 — **고침**

`server/app.js:106` 이 `SELECT *` 입니다. 16개 컬럼이 그대로 나갑니다.

화면이 안 쓰는 것이 여섯 개입니다.

| 컬럼 | 왜 필요 없나 |
|---|---|
| `x`, `y` | 원본 TM 좌표(EPSG:5181). `SearchMap.tsx:345` 가 받자마자 위경도로 **덮어씁니다** |
| `mgtno` | 클라이언트 참조 0곳 (적재용 키) |
| `lastmodts` | 참조 0곳 |
| `apvpermymd` | 참조 0곳 |
| `dcbymd` | 참조 0곳 |

실측 — 서울 도심 상자, 300건:

```
지금              139,598 B  (465 B/건)
여섯 컬럼 뺀 뒤    96,764 B  (323 B/건)
                 -42,834 B  (31%)
```

이 요청이 전체 전송량의 65% 이므로, 전체로는 **20%가 줄어듭니다.**

**고쳤습니다.** `server/app.js` 의 `FACILITY_COLUMNS` 로 열 개만 골라 보냅니다.
`x`·`y` 가 빠지면서 클라이언트도 같이 정리했습니다 — `PlaceData` 는 이제 서버가
보내는 것만 담고, 지도가 만들어 쓰는 `x`/`y` 는 `SearchMap.tsx` 의 `MappedPlace`
에만 있습니다. 덕분에 `as number` 여섯 개가 없어졌습니다(널이 아니게 됐으므로).

화면에서 확인한 것: 지도 마커·클러스터(시설 97개) → 마커 클릭 시 상세(이름·상태·
지번·도로명) → 후기 작성 화면(Redux 를 거친 `selectedPlace`) → 시설 검색 목록
(이름·상태·두 주소·전화번호). 브라우저가 실제로 받은 바이트 96,764 B,
콘솔 오류 없음(위치 권한 거부 제외). 300건 모두 좌표가 성해 마커로 그려집니다.

### 4. `/mypage/reviews` 는 사진을 그대로 싣습니다 — **고침**

`server/controller/mypage.js:41-43`

```js
// 후기에는 사진이 붙어 있어 더더욱 전부 내려보내면 안 됩니다.
const query = `SELECT * FROM reviews WHERE user_id = ? AND deleted_at IS NULL
                ORDER BY created_at DESC, review_id DESC LIMIT 20`;
```

주석은 맞는 말인데 `LIMIT 20` 으로 **건수만** 줄였습니다. `SELECT *` 라 `images`
컬럼이 그대로 따라갑니다.

같은 후기를 시설 목록은 이미 제대로 다룹니다 — `server/controller/review.js:76`
이 `COALESCE(JSON_LENGTH(images), 0) AS image_count` 로 장수만 보냅니다
(CLAUDE.md §2.5, 429KB → 725B 로 줄인 그 변경).

실측: 사진 2장짜리 후기 **하나**를 가진 계정의 `/mypage/reviews` 가 **214,370 B**
입니다. 시설 목록에서 같은 후기 다섯 건이 725 B 인 것과 견주면 300배입니다.

이번 시험에서 크게 안 보인 이유는 시드 데이터에서 사진 붙은 후기를 가진 사람이
1만 명 중 67명뿐이어서입니다. **상한은 `LIMIT 20` × `MAX_IMAGES` 5장 × 약
107KB = 10MB** 입니다. 후기를 열심히 쓴 사람일수록 마이페이지가 무거워집니다.

**고쳤습니다.** `review.js` 와 같은 컬럼 목록으로 바꿔 `image_count` 만 보냅니다.
같은 계정으로 재면 **214,370 B → 289 B (99.9%)** 입니다.

화면 타입은 고칠 것이 없었습니다 — `ReviewData` 는 진작 `image_count` 를 받기로
적어 두었고(`types/review.type.ts`), 이 칸은 사진을 그린 적이 없습니다
(펼친 상세에 `<img>` 0개). 서버만 타입이 적어 둔 대로 하지 않고 있었던 셈입니다.

화면에서 확인한 것: 마이페이지 후기 칸에 2건이 뜨고, 줄을 눌러 펼치면 작성 일시와
본문이 나옵니다. `image_count` 는 사진 2장짜리 후기에 2, 없는 후기에 0.
사진은 여전히 `GET /reviews/1/images` 로 214,064 B 가 받아집니다.

### 5. DB 풀은 병목이 아니었습니다

`DB_POOL_SIZE` 기본값 10 으로 200 VU 를 받았고, MySQL CPU 는 69%,
쿼리 지연은 전 구간 평평했습니다. 풀이 말랐다면 대기가 p95 에 나타났을 텐데
그런 흔적이 없습니다. 지금 건드릴 이유가 없습니다.

## 시험하면서 고친 것

부하를 걸기 전에 재는 판을 맞추느라 고친 것들입니다. 전부 측정 도구 쪽이고
앱 코드는 건드리지 않았습니다.

### 사본 DB 스키마가 뒤처져 있었습니다

`pet_vaccinations.due_time` 이 없어 **`/pets` 가 전부 500** 이었습니다. 앱 버그가
아니라 사본 DB 가 `alterVaccinationTime.sql` 이전 상태였던 것입니다.
`alterVaccinationTime` · `alterPushSubscriptions` · `alterVaccinationReminders`
세 개를 사본에 적용해 실제 스키마와 맞췄습니다.

처음에는 k6 요약이 "체크 97.5% 통과" 라고만 해서 무엇이 깨졌는지 알 수 없었습니다.
`loadtest/k6/lib/summary.js` 에 **깨진 체크 이름을 찍는 줄**을 넣어 찾았습니다.

### `seedScale.js` 에 빠진 것 두 가지

| 무엇 | 왜 문제였나 |
|---|---|
| `pet_vaccinations` 를 아예 안 넣음 | `/pets` 가 늘 빈 일정을 붙여 보내 실제보다 가볍게 나옵니다. 아이 하나당 5건씩 3만 행을 넣도록 했습니다 (`alterVaccinationReminders.sql` 이 인덱스를 잡으며 가정한 규모와 같은 숫자) |
| 댓글 6만 건을 글 2만 개에 **고르게** 나눔 | 글마다 3건이라 댓글 페이지네이션이 한 쪽도 안 넘어갑니다. 후기 쪽 `HOT_FACILITY` 와 같은 방식으로 `HOT_POST` 를 두어 한 글에 300건이 몰리게 했습니다 — CLAUDE.md 가 적은 "댓글 300건짜리 글" 경로가 그제야 밟힙니다 |

## 확인하지 못한 것

- **브라우저에서 눈으로 본 것이 없습니다.** API 응답만 봤습니다.
- **실제 망에서 재지 않았습니다.** 위 2·3번(전송량)은 localhost 라 지연에 안
  잡혔습니다. 실제 지연을 알려면 배포된 곳에 대고 다시 재야 합니다.
- **200 VU 위는 모릅니다.** 요청대로 200 에서 멈췄고, 거기까지는 꺾이지
  않았습니다. 한계를 알려면 더 올려 봐야 합니다.
- **클라이언트는 손대지 않아 빌드·테스트를 돌리지 않았습니다** (워크트리에
  `client/node_modules` 가 없습니다). 서버는 린트 0건 · 테스트 53개 전부 통과.
